# Telegram-бот Риты

Python 3.10+ и aiogram 3.25.0. Бот использует long polling и SQLite.
Видеоурок отправляет `start()`, предложение курса после видео —
`send_step(user_id, 2)` через 40 минут. Покупку обрабатывает `pay_cb()`.
Фотографии и клавиатуры этапов остаются прежними.

## Локальный запуск и проверки

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/ruff check .
.venv/bin/python -m compileall -q bot.py tests
```

Создайте `.env` самостоятельно, не добавляя его в Git, и ограничьте права:
`chmod 600 .env`. Обязательная переменная — `BOT_TOKEN`.
`DB_PATH` необязательна; локально по умолчанию используется `bot.sqlite3`
в рабочем каталоге. Сам Python-файл `.env` не загружает:

```bash
set -a
source .env
set +a
.venv/bin/python bot.py
```

Не запускайте локальную копию одновременно с серверной с тем же токеном.
Тесты используют фиктивный токен, временные базы и подмену Telegram API;
они не отправляют сообщения и не затрагивают рабочую базу.

## Скидка

`users.discount_until` — существующее постоянное поле, без новой таблицы.
До успешной отправки текста этапа 2 значение отсутствует. После ответа
Telegram сохраняются время отправки в `queue.sent_at` и срок скидки
через ровно 3600 секунд в одной транзакции. Для точности сохраняются
доли секунды (SQLite допускает REAL в колонке с INTEGER affinity).
При `now < discount_until` тарифы 2333 / 3888 ₽; при равенстве
и позднее — 3333 / 5555 ₽. В тестовом режиме для администраторов
(ADMIN_IDS) интервал сообщений и скидка сокращаются до 10 секунд.
При старте очищаются ошибочно рассчитанные прежней версией сроки
для ещё не отправленных предложений. Уже отправленные предложения
сохраняют свой записанный срок. Повторный `/start` таймер не обновляет.

Подтверждение Telegram и запись SQLite — разные системы: аварийное
завершение между ними может вызвать повторную отправку при восстановлении.
При обычных перезапусках записанный срок сохраняется.

Сценарий отправки чека сохранён. Поскольку тариф выбирается переводом,
бот не знает, какой из двух тарифов оплачен: администратору показываются
оба тарифа на момент получения чека, фактическая сумма проверяется по чеку.

## Развёртывание на Ubuntu

1. Убедитесь, что прежний бот остановлен (и его автозапуск отключён).
   Проверьте старый хост, локальные процессы, Docker и прочие известные
   места запуска. Telegram не предоставляет список всех polling-процессов.
   Если есть webhook, сначала разберитесь с прежним развёртыванием;
   не удаляйте webhook автоматически.
2. Сохраните актуальную SQLite-базу через `sqlite3.Connection.backup()`.
   Перед переносом проверьте `PRAGMA integrity_check`. Не копируйте только
   основной файл у работающей WAL-базы: часть данных может находиться в WAL.
   Не заменяйте существующую серверную базу без отдельного согласования.
3. Разместите Git-репозиторий в `/opt/rita-bot/repo` (GitHub clone или Git
   bundle из текущего репозитория), origin — `git@github.com:kolonizer/TG_RITA.git`
   либо HTTPS URL. Для приватного репозитория добавьте read-only deploy key
   самостоятельно; не переносите личный приватный SSH-ключ на VPS.
4. Выполните от root `bash /opt/rita-bot/repo/deploy/provision.sh`.
   Скрипт устанавливает только `python3-venv`, `git`, `ca-certificates`,
   создаёт системного пользователя `rita-bot` и юнит. Он не запускает бота.
   Приведите владельца репозитория к `rita-bot:rita-bot`.
5. Самостоятельно заполните `/etc/rita-bot/.env` с правами `root:root 600`:
   `BOT_TOKEN` и `DB_PATH=/var/lib/rita-bot/bot.sqlite3`.
   systemd читает этот файл до перехода к непривилегированному пользователю.
   Не печатайте содержимое `.env` и не вставляйте токен в команды или Git.
6. Если требуется миграция, перенесите согласованную актуальную базу в
   `/var/lib/rita-bot/bot.sqlite3`, владелец `rita-bot:rita-bot`, права `600`.
7. Подготовьте release из проверенного Git-коммита:
   `/opt/rita-bot/releases/<SHA>` с собственным `.venv` и зависимостями
   `requirements.txt`. Запустите тесты внутри release. Создайте симлинк
   `/opt/rita-bot/current` на этот каталог. Проверьте юнит командой
   `systemd-analyze verify /etc/systemd/system/rita-bot.service`.
8. После проверки токена, отсутствия webhook и второго экземпляра:
   `systemctl enable --now rita-bot.service`.
   Проверьте статус и логи, в том числе отсутствие `Conflict` и перезапусков.

Рабочие данные расположены в `/var/lib/rita-bot`, секреты — в `/etc/rita-bot`,
код — в `/opt/rita-bot`. Автоперезапуск: `Restart=on-failure`, задержка 5 секунд.
Firewall и SSH-конфигурация скриптами не меняются.

## Статус, логи и обновления из GitHub

```bash
ssh root@72.56.122.42
systemctl status rita-bot.service --no-pager
journalctl -u rita-bot.service -n 100 --no-pager
journalctl -u rita-bot.service -f
```

Сначала проверьте новый коммит локально и отправьте его в GitHub.
На сервере используйте полный SHA проверенного коммита:

```bash
sudo bash /opt/rita-bot/repo/deploy/update.sh <полный-SHA-коммита>
```

Скрипт получает коммит из GitHub, готовит отдельный release и virtualenv,
запускает тесты, останавливает единственный сервис, делает резервную
копию базы в `/var/backups/rita-bot`, переключает симлинк и запускает сервис.
При неудачном запуске возвращает предыдущий код, сохраняя базу.
Проверьте логи и ручную покупку через тестового пользователя.
Старые releases и резервные копии автоматически не удаляются.
Обновления запускайте после согласованной миграции и заполнения `.env`.

## Быстрый тестовый режим

В `/etc/rita-bot/.env` переменная `TEST_MODE=true` включает интервалы
и скидку по 10 секунд только для ADMIN_IDS (313372023, 893519113).
У остальных пользователей сохраняются обычные сроки. По умолчанию
`TEST_MODE=false`. Тексты, фотографии и кнопки остаются прежними.

Для переключения подключитесь к серверу и выполните:

```bash
cd /opt/rita-bot/repo/deploy
python3 test-mode.py on
```

Чтобы вернуть обычные сроки:

```bash
python3 test-mode.py off
```

Скрипт меняет сохранённый режим в SQLite и перезапускает сервис.
Секреты не выводятся. Сохранённые очереди и сроки скидки не пересчитываются.
Для нового теста администратор отправляет боту `/reset`, затем `/start`.
После выключения также используйте `/reset` и `/start` для своего аккаунта,
если хотите пройти обычную воронку: уже записанные быстрые задания продолжают
исполняться до завершения или сброса. Других пользователей сбрасывать не нужно.

Проверка режима и сервиса в терминале (без перезапуска):

```bash
python3 test-mode.py status
```

В Telegram администраторы также могут отправить `/status`: бот покажет
режим, длительность новых таймеров и остаток собственной скидки.
Режим переключается через терминал VPS или команды `/test_on` и `/test_off` в Telegram.


`/stats` и `/status` показывают число пользователей, начавших воронку
за период, число полученных чеков за период, текущие ожидания чека и
общее число пользователей в базе. `/reset_stats` начинает новый период
(постоянный маркер `stats_period.since` в SQLite), не удаляя пользователей,
чеки, очередь и сроки скидки. `/reset` по-прежнему сбрасывает только
собственное прохождение; статистика отражает текущие записи пользователей.
В терминале тот же сброс выполняет `python3 test-mode.py reset-stats`.
Для новых чеков сохраняется `users.receipt_received_at`; прежние записи
без даты учитываются только в статистике за всё время. Полученный чек
не означает автоматически проверенную администратором оплату.


Переключение непосредственно в Telegram для ADMIN_IDS:
`/test_off` — обычный режим; `/test_on` — тестовый по 10 секунд.
Команды применяются сразу без перезапуска сервиса. Выбор хранится в
`runtime_settings` в той же SQLite-базе и переживает перезапуски.
`TEST_MODE` из `.env` используется только для первоначального значения,
когда сохранённого выбора ещё нет. Терминальный переключатель обращается
к той же записи; `/status` и терминальный `status` показывают один режим.
Существующие очереди и скидки сохраняются: для прохождения заново с
новыми таймерами отправьте `/reset`, затем `/start` со своего аккаунта.
